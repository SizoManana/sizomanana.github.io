Portfolio design system

The rules behind the presentation

This page is deliberately supporting material, not a case study. It documents enough of the portfolio's visual and interaction system to show that the site itself is treated as a designed product, without asking a recruiter to read a technical manifesto before seeing client work.

Visual languageNear-black, warm paper and one emerald accent with square, editorial blocks.
TypeSystem fonts only, strong scale and hierarchy instead of relying on a display typeface.
InteractionClear focus, real buttons and links, minimal motion and progressive disclosure for very long imagery.
ResponsiveFixed sidebar becomes a sticky top bar; grids collapse deliberately rather than merely shrink.

Intent

Editorial rather than portfolio-template neutral

The system uses a dark fixed navigation rail, filled section bars, heavy headings, strong borders and alternating paper/dark bands. The purpose is not visual novelty. It gives long-form case studies enough hierarchy that a recruiter can skim while a hiring manager can keep reading.

Primary ruleThe portfolio should never make a stronger claim than the case evidence can support. Measured outcomes are labelled as measured, limitations stay visible, and work without validation does not receive invented performance numbers.

Colour and contrast

One accent, two schemes

Light and dark modes are treated as separate contrast relationships rather than one palette mechanically inverted. Emerald behaves differently on light and dark surfaces so buttons, links and section bars remain legible.

Light

Warm off-white surfaces, near-black text, darker emerald for filled accents.

Dark

Near-black/green surfaces, light text and a brighter emerald where the accent sits directly on dark.

The detailed token implementation lives in assets/css/site.css and the V2 extensions in assets/css/v2.css.

Component rules

A small vocabulary repeated consistently

Project cards

Image, numbered marker, discipline kicker, concise project proposition and a clear route into the case.

Evidence strips

Problem, evidence, intervention/constraint and outcome/learning give recruiters a fast read before the long-form story.

Follow the thinking

The case-study navigation is intentionally high-contrast and separated from surrounding content so long pages can be scanned non-linearly. Once it reaches the viewport it stays available as a compact pinned strip with a direct route back to the top.

Callouts

Used for limitations, lessons and decisions that should not disappear inside body copy.

Full-page viewers

Long website screens stay contained in a scrollable viewer so they do not turn the portfolio itself into a 15,000-pixel image dump.

Progressive image reveal

Very long mobile screens can be clipped and expanded, with the full content still available when scripting is unavailable.

Accessibility and interaction

Constraints that shape the interface

  • Keyboard visibility: interactive elements retain a visible focus treatment.
  • Semantic controls: navigation uses anchors, actions use buttons, and long image disclosure exposes its expanded state.
  • Reduced motion: motion is decorative rather than required to understand content.
  • Image meaning: alt text describes the useful visual evidence rather than labelling everything “screenshot”.
  • Responsive navigation: evidence grids collapse into readable blocks; the pinned in-page navigation becomes a compact horizontal strip so it stays available without consuming the mobile viewport.
  • Zoom and reflow: the layout is allowed to reflow rather than preventing browser zoom.

Build logic

Static by choice

The portfolio is plain HTML, CSS and lightweight JavaScript. That keeps the implementation inspectable, reduces third-party dependencies and makes it easier to keep the case-study structure consistent. The public GitHub repository is the technical evidence layer for anyone who wants to inspect how it is assembled.

The portfolio is not the product-design claim. Client systems, PINE, CPQ work and measured CRO engagements carry that burden. This page simply shows that the presentation layer follows the same habit of writing constraints and decisions down.
