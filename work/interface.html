Interface and systems

The craft that gets scattered across case studies

The client stories explain outcomes. This page isolates the interface decisions underneath them: fixed component constraints, system states, reusable patterns, responsive behaviour and accessibility.

ConstraintsDesigning with real platform components instead of idealised mock components.
StatesEmpty, partial failure, blocking, rejection and recovery treated as first-class flows.

Platform constraint

Designing inside a component library you cannot override

HubSpot UI extensions permit no custom CSS. The interface has to be expressed through the platform's components at the sizes they actually ship.

In the Cambridge CPQ, the native Input, Select and DateInput controls were 240 pixels wide. Three native editable controls could not coexist inside the available card width, so the table used compact value cells that open the real control on interaction. The pattern came from measurement, not preference.

The product-design pointA technically impossible layout is not solved by making the Figma frame look cleaner. The component constraint has to shape the interaction.

Reusable behaviour

Systems, not screens

The pieces that decide whether a site survives growth are usually the less glamorous ones: search behaviour, filters, navigation, states and page templates that still work when the content set changes.

State design

The states are the design

The happy path proves that a feature can work. Failure and recovery states determine whether users trust it when reality becomes messy.

State is not decorationEach condition changes what the user can safely do next, what the system knows, and what feedback is required.

Responsive systems

Templates and mobile that survive the first handoff

The design should still make sense when a marketing team adds a page I never drew or when the same information has to work at 375 pixels.

Mobile designed, not squeezed

Accessibility constraints

Accessibility changes the design before it becomes a checklist

Contrast is the obvious visual example. This portfolio's emerald accent cannot use the same foreground relationship as a light yellow reference colour. The colour token therefore changes behaviour depending on the surface instead of copying the visual treatment mechanically.

What that means in practice

Visible focus treatment, semantic controls, logical heading structure, meaningful alt text, reduced-motion support, zoom that is never disabled, and responsive layouts that do not require hover-only interactions. Accessibility is considered alongside the interaction, not added as an annotation after the screen is finished.
